# PHASE2 — Project Template Auto-Wire Anchors (the ONE change to an already-shipped template)

Parent: `PHASE0_MASTER_STRATEGY.md` (read it first, in full).
Design doc Step: Step 2B of
`DESIGN_REQUIREMENTS_ONSCREEN_COMPOSITING_BIGSTEP_02_EDITOR_INTEGRATION_2026-09-29.txt`
— **read that Step's own full text before starting; it is the load-bearing
justification for a real, deliberate, necessary dependency this phase adds
onto a different, already-shipped campaign's own template
(`editor-core-separation-16`'s "Create New Project" feature). This is
intentional, not scope creep.**

## Step 1: The Goal

The auto-wire mechanism (PHASE4) needs two stable, exact, machine-readable
anchor comments already present in a project's own `<ProjectName>Game.cpp`
before it can safely find WHERE to insert anything. Those anchors do not
exist in the current "New Project" template. This phase adds them, for every
NEWLY-CREATED project going forward — and ONLY for newly-created projects;
every already-existing project's own `<ProjectName>Game.cpp` is explicitly,
permanently left untouched (Non-Goal, restated in PHASE0's own Locked
Decision 7).

`src/Editor/EditorProjectLifecycleCapability.cpp`'s `BuildGameStubCppContent()`
(lines 59-82), the CURRENT, byte-for-byte template, called by
`CreateNewProjectAssembly()` (line 374:
`WriteTextFile(assetsDirectory / (name + "Game.cpp"), BuildGameStubCppContent(name));`):


## Step 3: The Plan

Replace `BuildGameStubCppContent()`'s body with the REQUIRED new template
(byte-for-byte, per the source design document's own Step 2B):

```cpp
std::string BuildGameStubCppContent(const std::string& name)
{
    return
        "// " + name + "Game.cpp - generated by the Editor's \"Create New Project\" action.\n"
        "// This is your project's Game half's entry point. Add your own render\n"
        "// passes/ECS components/systems here, or use the \"Project\" panel's\n"
        "// right-click \"Create\" menu (once this project is open/active) to scaffold\n"
        "// a starting Render Pass / Compute Shader / Vertex+Fragment Shader pair.\n"
        "#include \"../Libraries/ProjectAssemblyExports.h\"\n"
        "#include \"../../../src/Core/Core.h\"\n"
        "\n"
        "// GTE_AUTO_REGISTER_FORWARD_DECLARATIONS - do not remove or edit this\n"
        "// line. The Editor's \"Create\" scaffolding tools (Render Pass / Compute\n"
        "// Shader / Screen Post-Process Pass) insert a forward declaration for\n"
        "// each newly-scaffolded Register<Name>...(core) function directly BELOW\n"
        "// this line, automatically. Removing this comment does not break\n"
        "// anything - a future scaffold action simply cannot auto-wire itself in\n"
        "// anymore, and falls back to reminding you to wire it in by hand instead.\n"
        "\n"
        "namespace {\n"
        "\n"
        "void RegisterProject(gte::Core& core)\n"
        "{\n"
        "    // GTE_AUTO_REGISTER_ANCHOR - do not remove or edit this line. The\n"
        "    // Editor's \"Create\" scaffolding tools insert their own\n"
        "    // Register<Name>...(core); call directly ABOVE this comment,\n"
        "    // automatically, when they can find it. Removing this comment does\n"
        "    // not break anything - a future scaffold action simply cannot\n"
        "    // auto-wire itself in anymore, and falls back to reminding you to\n"
        "    // wire it in by hand instead.\n"
        "}\n"
        "\n"
        "} // namespace\n"
        "\n"
        "GTE_DEFINE_PROJECT_EXPORTS_GAME(RegisterProject)\n";
}
```

Two exact, load-bearing changes from the original, both must be applied
together:
1. The parameter is now `gte::Core& core` (named, not commented out) — a
   required, mechanical consequence of inserted calls needing to reference
   `core` by name; a commented-out parameter would produce inserted code
   that fails to compile.
2. Two new anchor comments, at the two exact insertion points PHASE4's helper
   searches for — the EXACT literal text
   `"// GTE_AUTO_REGISTER_FORWARD_DECLARATIONS - do not remove or edit this line."`
   and `"// GTE_AUTO_REGISTER_ANCHOR - do not remove or edit this line."` must
   appear verbatim (PHASE4's helper does a plain `std::string::find()` for
   these exact strings — any deviation, even whitespace, breaks auto-wiring
   silently for every future project).

**Nothing else in this file changes.** `CreateNewProjectAssembly()`'s own
call site (line 374) does not need to change at all — it already just calls
`BuildGameStubCppContent(name)` and writes whatever string comes back.

**Worth noting, not a required change**: the template's own header comment
(line 4 of the generated file, "...to scaffold a starting Render Pass /
Compute Shader / Vertex+Fragment Shader pair.") still lists only the three
PRE-EXISTING scaffold kinds by name, never mentioning the new "Screen
Post-Process Pass" option this whole campaign adds. The source design
document's own Step 2B gives this template's text byte-for-byte and does not
ask for that comment to be updated, so this phase does NOT change it — but if
the implementer judges a one-word-list update ("...Render Pass / Compute
Shader / Vertex+Fragment Shader pair / Screen Post-Process Pass.") to be a
clear, harmless, non-load-bearing improvement, that is a reasonable,
independent judgment call to make (record it in the completion report either
way — whether it was changed or deliberately left as specified).

## Step 4: Honest, explicit consequence (restate this in the completion report)

Every project created BEFORE this phase ships (including
`Projects/ProjectAssemblyProbe/` and any project a user already made) has
NEITHER anchor, and `gte::Core& /*core*/` still has its parameter commented
out. Per PHASE4's own "missing anchor = do nothing, fall back to the
reminder message" contract, scaffolding a NEW Screen Post-Process Pass into an
OLD project (once PHASE6 lands) is still 100% safe — it simply falls back to
the original, fully-manual "remember to add this line yourself" behavior for
that one project, forever, unless a human manually adds the two anchors and
un-comments `core` themselves. This phase does NOT retroactively rewrite any
existing project's `<ProjectName>Game.cpp`.

## Step 5: Verification (this phase only)

1. Incremental build (`cmake --build build`) — confirm it compiles cleanly.
2. Live check: use the Editor (or `POST /project_assembly/create_project`) to
   create a brand-new, throwaway test project (e.g. `TemplateAnchorSmokeTest`)
   and read its generated `Assets/TemplateAnchorSmokeTestGame.cpp` back
   (`read_file`) — confirm BYTE-FOR-BYTE it contains both anchor comments in
   the correct positions and `gte::Core& core` (not commented out). Confirm
   the project still compiles cleanly as-is (an empty `RegisterProject()`
   body is still perfectly valid C++) via an incremental build of that
   project specifically, or the whole solution.
3. Delete this throwaway smoke-test project's folder afterward (it is
   NOT the permanent PHASE8 fixture — that one is created fresh, later, in
   PHASE8 itself, specifically to prove the FULL auto-wire feature after
   every phase has landed; this phase's own smoke test only proves the
   template text itself is correct).
4. No new Tier-1 test is strictly required for a pure string-literal template
   change like this one. `tests/Editor/AssetScaffoldTemplateTests.cpp` already
   exists (confirmed) and is the right place if the implementer wants a cheap
   insurance test (a plain `std::string::find() != npos` check for both exact
   anchor literals, exercised indirectly by creating a real project the same
   way `CreateNewProjectAssembly()`'s own existing tests already do, if any
   exist under `tests/Core/` for it) — optional for this specific phase, since
   PHASE8's own live verification (Step 5.2) already proves this template's
   real output byte-for-byte against a real generated file.
